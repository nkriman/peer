  The new test only validates that a `UUID` with `version=None` is rejected by versioned fields (`UUID1`, `UUID3`, `UUID4`, `UUID5`). It does not test that the same UUID is **accepted** when used with an unversioned `UUID` field — which is the actual bug being fixed (issue #7355). The happy-path assertion `assert m.model_dump() == {'a': a, 'b': b, 'c': c, 'd': d, 'e': e}` above does cover this (since `e` is assigned to a plain `UUID` field), but there is no standalone or targeted test that directly exercises the fix (e.g. a model with only `v: UUID` and input `UUID('{00000000-7fff-4000-7fff-000000000000}')`) to make the intent obvious and to ensure regression coverage if the test structure changes.
  -- The bug in #7355 is that a UUID with `version=None` caused a crash or incorrect validation failure on plain `UUID`-typed fields. The only place that exercises the fix is the combined `m = UUIDModel(a=a, b=b, c=c, d=d, e=e)` assertion, which is indirect. A dedicated, minimal test for the `UUID` (unversioned) field case would make the coverage intent explicit and resilient to future test refactoring.
